# This directory is a spending ledger

Everything here was generated by `spend agent build` from an append-only encrypted log. It is
a **snapshot, not a live view**, it exists only while the store is unlocked, it lives in
tmpfs, and it is gone at `spend lock`.

Nothing here is editable. The next build overwrites anything you change. If a number is
wrong, the fix is a correction in the app — `spend` — not an edit here.

**Read `MANIFEST.json` first.** If a question reaches past what its `coverage` says is here,
say so before you answer it.

## Read this before you sum anything

There are five ways to be confidently wrong with this data. Each has a rule.

### 1. Sum `net_spend_cents`. Never sum `amount_cents`.

`amount_cents` is signed the way a statement is signed: **negative means money left the
account.** A $4.75 coffee is `-475`. Sum that and you get a negative number, and you will then
either report negative spending or flip the sign somewhere and be wrong about the refunds.

`net_spend_cents` is already positive-for-spending, already negative for refunds, and already
**exactly zero** for transfers, credit-card payments, income, tombstones, and rows whose
amount could not be parsed. It is safe to sum over any subset of any file here with no
`WHERE` clause at all. That is what it is for.

### 2. Everything is integer cents. Divide once, at the very end.

There are no dollar floats in this directory and you should not create any. `0.1 + 0.2` is
why. Add in cents; format once:

```python
f"${total // 100:,}.{total % 100:02d}"
```

Each row also carries `amount`, a decimal string. It is **display only**. Do not do
arithmetic on it and do not call `float()` on it.

### 3. A credit-card payment is not spending, and it is in here twice.

When $1,204.11 moves from checking to the Quicksilver card, this ledger holds both legs:
`-120411 CAPITAL ONE AUTOPAY PYMT` on `cap1-checking`, and `+120411 PAYMENT THANK YOU` on
`cap1-quicksilver`. Neither is spending. The spending was the individual charges on the card,
and those are already here.

Both legs carry `flow: "payment"` and `net_spend_cents: 0`, so rule 1 handles this for you.
But if you ever find yourself aggregating `amount_cents` or `outflow_cents` directly — stop.
You have just added a year of card payments to a year of purchases. The same applies to
`flow: "transfer"` between checking and savings.

### 4. `receipts/` is not more spending. It is the same spending, in detail.

`bank/` is what the accounts reported. `receipts/` is what was photographed. They describe
overlapping reality and **they are not deduplicated** — the $47.03 at Trader Joe's is very
likely in both.

So every row in `receipts/` has `net_spend_cents: 0`, by construction, and `ledger.db`
enforces it with a `CHECK` constraint. You can `cat` every `.jsonl` file in this directory
into one stream, sum `net_spend_cents`, and still get the bank total — that is true
literally, and every `.jsonl` file here is transaction rows and nothing else:

```bash
cat bank/*/*.jsonl receipts/*/*.jsonl | jq -s 'map(.net_spend_cents) | add'
```

Use `bank/` when the question is **how much**. Use `receipts/` when the question is **what was
in the bag** — line items, tax, tip, which specific groceries, what a vague charge actually
was. A receipt's own total is `total_cents`, positive; if you use it, scope the answer to
receipts and say that you did.

### 5. Pending is provisional, and it is still real.

A row with `"pending": true` has not settled, and its amount can still change. A restaurant
that authorises $52.00 and posts $61.00 once the tip clears is the normal case, not an
anomaly — and you can watch it happen: `revisions` counts how many times the bank restated
the row, and `amount_changed` is true when one of those restatements moved the money.

Pending rows **are** included in `net_spend_cents`, because they are real purchases. Exclude
them only when reconciling against a printed statement, and when you do, say so.

## The shape of a row

Every `.jsonl` file under `bank/` and `receipts/` holds one JSON object per line, sorted by
date, one file per calendar month. Both streams share one envelope, so `cat **/*.jsonl` is
coherent. `SCHEMA.md` has every field with its type and whether it is safe to sum. These are
the ones you will actually use:

| field | |
|---|---|
| `date` | the day to group by. Local calendar date. Use this, not `posted_on`. |
| `net_spend_cents` | the only field you sum. Positive = spent, negative = refunded. |
| `merchant` | normalised and comparable — `Blue Bottle Coffee` |
| `description` | verbatim from the bank — `SQ *BLUE BOTTLE COFFEE   BROOKLYN NY` |
| `category` | one of ten. `categories.json` lists them. |
| `flow` | `spend` `refund` `fee` `income` `transfer` `payment` `unknown` |
| `account` | your account keys — see `accounts.json` |
| `stream` | `bank` or `receipt` |

## How to answer a question

**Prefer SQL.** `ledger.db` holds exactly the rows in the `.jsonl` files, indexed.

```bash
spend agent sql 00-monthly-by-category.sql

spend agent sql "SELECT merchant, SUM(net_spend_cents) AS cents
                 FROM spending WHERE date >= '2026-08-01'
                 GROUP BY 1 ORDER BY cents DESC LIMIT 20"
```

`spend agent sql` takes SQL, a path, or the name of a file in `queries/`, and it is always
available. The `sqlite3` binary is nicer if this machine has it — but it is a separate
package and often is not installed, so do not conclude the database is missing when the
*tool* is:

```bash
sqlite3 -header -column ledger.db < queries/00-monthly-by-category.sql   # if you have it
```

**Start from the `spending` view, not the `bank` table.** `spending` is
`bank WHERE counts_as_spending = 1`; it has already dropped the transfers, the card payments,
the income, and the rows that failed to parse.

`queries/` holds eight worked queries. **Read the relevant one before writing your own** —
they encode decisions (what counts as recurring, where a month boundary falls, what makes a
charge unusual) that are not worth re-deciding per question, and each says in its header what
it does *not* count.

Use `jq` and `grep` for lookups and spot checks. Use SQL for anything that aggregates.

```bash
grep -h 'Blue Bottle' bank/2026/*.jsonl | jq -r '[.date, .amount, .description] | @tsv'
```

## Say what you do not know

`MANIFEST.json` carries `coverage`, `feed_health` and `warnings`. Three failures to avoid:

- **A quiet month and a broken feed look identical.** If `feed_health.simplefin.stale_days`
  is above 2, the last weeks are incomplete. Say so before reporting a trend.
- **Apple Card arrives by hand.** It is a CSV or OFX export dropped into a folder, so its
  coverage usually starts later and ends whenever somebody last exported. Check the
  per-account `covers_to` in `MANIFEST.json` before comparing accounts, or before concluding
  that a card went quiet.
- **`warnings` is a list of things the build already knows are wrong.** Read it. Unmapped
  accounts and unrecoverable gaps show up there.

Also check `duplicate_suspect`. A true value means two rows look like the same purchase
arriving from two different sources — usually a file import overlapping the live feed. They
have not been merged, and if one lands inside a total you are reporting, mention it.

## Tone

Answer the question. Cents-accurate, with the period and the accounts stated once. If a
category looks odd, read `description` before concluding anything — the categoriser matches
substrings and it is wrong sometimes, and a mis-filed $9 charge is not a finding.

Do not moralise about spending. Do not round to make a point.
